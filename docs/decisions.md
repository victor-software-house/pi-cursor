# pi-cursor decisions

> **Status:** `pi-cursor-inference@0.0.2` released 2026-09-03. npm integrity, exact tag and GitHub
> Release, clean Pi installation, corrected README links, and pi.dev's native 4K 16:9 gallery
> rendering are verified.

> Earlier decisions below are chronological. Later entries explicitly supersede earlier scope or
> evidence decisions.

- 2026-09-02 Public package `pi-cursor-inference` on npm (unscoped, MIT; GitHub repository stays `pi-cursor`) is a clean proof of concept of Cursor as a plain inference provider over `aiserver.v1.InferenceService/RunInference`. It is not a port of the private `@victor-software-house/pi-cursor` extension's operator features.
- 2026-09-02 Scope is a working provider plus login. The usage dashboard is out; it is larger than the provider and not yet fully tested.
- 2026-09-02 Machine identity is derived from the host with Cursor's own algorithm, never read from an installed IDE. Evidence: Cursor 3.18.9 `main.js` (`id.js`, `macAddress.js`, `telemetryUtils.js`): `telemetry.machineId` = SHA-256 of the OS hardware id string (`ioreg` IOPlatformUUID on darwin, `MachineGuid` on win32, `/etc/machine-id` or hostname on linux, `smbios.system.uuid` on freebsd; random UUID fallback); `telemetry.macMachineId` = SHA-256 of the first `os.networkInterfaces()` MAC not in `{00:00:00:00:00:00, ff:ff:ff:ff:ff:ff, ac:de:48:00:11:22}`. Both recomputed locally on 2026-09-02 and equal to the IDE's stored values byte for byte. The checksum omits the `/mac` suffix when no MAC exists, as Cursor does.
- 2026-09-02 `x-cursor-client-os` and `x-cursor-client-arch` follow `process.platform` / `process.arch`, matching Cursor's `getClientOS()`. The private extension's `darwin`/`arm64` hardcode is not carried.
- 2026-09-02 Credentials use Pi's native OAuth provider contract (`auth.oauth` with `login`, `refreshToken`, `getApiKey`) so `/login cursor` works and Pi owns storage and refresh. No SQLite, no 1Password, no keychain reads. A `PI_CURSOR_TOKEN` environment variable remains the headless path.
- 2026-09-02 Single account. Multi-account is deferred until a public user asks for it.
- 2026-09-02 The reconstructed `inference.proto`, the artifact lock (version, commit, URL, DMG hash, module ids), and a synthetic tool round-trip corpus are committed as public evidence of the wire contract. The DMG, extraction scripts, and network drift gates from the private repository are not carried.
- 2026-09-02 Repository starts private and becomes public at the first npm release.
- 2026-09-02 npm rejected `pi-cursor` (“too similar to existing package cli-cursor”) and `pi-cursor-provider` was taken. `pi-cursor-inference@0.0.0` was published manually by the operator as the name reservation and Changesets bootstrap; the first functional release is `0.0.1` through the Version Packages PR. Port only the runtime required for provider registration, OAuth login/refresh, host-derived identity, catalog preflight, RunInference request/transport/stream mapping, and their narrow tests. Do not carry account/database abstractions, operator commands, usage UI, keychain/1Password support, capture/extraction machinery, broad CLI proto trees, or historical artifacts.

Explicit tree shaking plus packed-bundle checks must prove unused type-kit modules, package names, and source paths are absent. No other private package dependency is permitted.

- 2026-09-02 Operator resumed development the same day. The login challenge derivation was corrected to `base64url(sha256(verifier-string))`: the captured 2026-08-25 poll exchange reproduces the server challenge exactly from the verifier string, and the extracted CLI, IDE agent-host, and SDK auth clients use the same derivation. Hashing the raw 32 verifier bytes (the previously committed form) produces a challenge the server never accepts, so polling stays 404 until timeout. Release automation remains disabled pending an explicit operator decision.
- 2026-09-02 Measured live login and refresh. The corrected challenge derivation completed a real browser login and poll. `POST /auth/exchange_user_api_key` rejects both login JWTs as bearer with 401 `Invalid User API Key` (access and refresh both measured); that endpoint consumes only a Cursor User API Key, which the CLI stores as a separate `cursor-api-key` credential that browser logins never write. The CLI, IDE agent-host, and SDK never refresh a browser login at all: their refresh callbacks bearer `getApiKey() ?? CURSOR_API_KEY` and keep the current token when absent.
- 2026-09-02 Exhaustive extracted-source audit found the real refresh mechanism in the pinned 3.18.9 IDE workbench, and it was measured live: `POST https://api2.cursor.sh/oauth/token` with `{grant_type: "refresh_token", client_id: "KbZUR41cY7W6zRSdpSUJ7I7mLYBKOCmB", refresh_token: <PKCE login refresh JWT>}` returns 200 with a fresh 60-day `access_token` (plus `id_token` and `shouldLogout: false`). The refresh JWT is durable and non-rotating: repeated grants with the same token each returned 200, and the response carries no `refresh_token`. The `x-cursor-client-type` header the workbench sends is optional (measured 200 without it). The workbench skips the grant while the access JWT has more than ~53 days left (`Qrr = 1272*60*60*1e3 ms`) and stores the new access token as both access and refresh; pi-cursor instead keeps the original refresh token, which stays valid. `shouldLogout: true` means server-side revocation (e.g. MDM sign-in policy) and is surfaced as a re-login error. oh-my-pi's `exchange_user_api_key` refresh prior art is wrong (measured 401 for both JWTs).
- 2026-09-02 The first live `/login cursor` proof succeeded end to end, but completing the login in the browser launched the installed Cursor IDE: the portal defaults a missing `redirectTarget` to `ide` (its JS accepts `{cli, origin, sand}`, else `ide`) and fires the Cursor deep link on completion, which macOS routes to the installed app. The poll was unaffected. pi-cursor now sends the portal's own `redirectTarget=cli` — the CLI's actual parameter — which suppresses the deep-link launch and changes nothing in the auth contract (same challenge, poll, and refresh endpoints).

Private build dependencies are bundled like `pi-type-kit`.
- 2026-09-02 Operator set the parity rule: auth and refresh must come from the same client whose inference pi-cursor mirrors — no mixing clients and no unsupported fields. The pinned inference transport is the IDE 3.18.9 agent-host (`657.js`), and its credential provenance is now traced end to end: the agent-host extension's `credentialManager` (`Is` class in `extensions/cursor-agent-host/dist/main.js`) reads `cursor.getCursorAuthToken()` — the workbench-managed token — its `getApiKey()` is always undefined, and its `setAuthentication` merely executes the `cursorAuth.triggerTokenRefresh` command. The IDE's credential lifecycle is therefore entirely workbench-owned: workbench PKCE login → `storageService` (`cursorAuth/accessToken`/`cursorAuth/refreshToken`, not the CLI keychain) → agent-host consumes the token for inference → workbench renews it. pi-cursor's auth was realigned to the workbench in the same change: login URL sends `supportsSelectedTeamLogin=true` (the later portal-redirect decision above adds the CLI target solely to suppress the IDE deep link); the poll is a fixed 500 ms GET interval for the ~180 s window with no backoff and no error cap (the workbench interval swallows transient failures), sending the workbench header set (`traceparent`, `x-ghost-mode: implicit-false`, `x-new-onboarding-completed: false`, `x-cursor-client-type: ide` — the workbench's own default-state values); the refresh grant adds `x-cursor-client-type: ide` and the workbench's 20 s deadline; a `403` poll carrying the MDM sign-in-policy sentinel surfaces as a policy error while every other failure keeps polling. The workbench's store-access-as-refresh quirk stays uncopied (measured deviation, recorded above). The CLI-shaped 150-attempt backoff poll and the `PI_CURSOR_API_KEY` refresh branch were removed.
- 2026-09-02 Operator required Max Mode to default off and remain configurable. - 2026-09-02 Operator required the RunInference mapper to stop silently discarding known response arms. Every received arm is counted in a `cursor-inference-response` diagnostic. The request builder also forwards the IDE's explicit `max_tokens`, `temperature`, `top_p`, and `stop_sequences` model config fields.

- 2026-09-03 Final reconciliation is an always-on provider invariant, not a warning layer. Reasoning metadata matches by exact signature, then exact full text. A metadata-only final block may attach to streamed text by cardinality only when exactly one unmatched block exists on each side. Multi-block unmatched metadata remains as separate continuation blocks and is never paired by array index. Every bounded live inference test asserts the reconciliation diagnostic, and a paid arbitrary-tool turn proves exact streamed/final tool equality before continuation.
